# Agent Note：run_code 解析失败携带补救提示与未闭合字面量行号

Status: implemented

[English](2026-08-18-run-code-parse-failure-diagnostics.md) | 中文

## 问题

解析失败的程序体以裸消息到达模型：类型剥离阶段的 `Expected ',', got '<eof>'`，或 V8 `SyntaxError`（栈里只有合成函数帧）。两者都不带行列，模型无法区分程序文本损坏与工具调用损坏，只能盲目重试——单会话内反复观测到。

## 决策

两个解析面现在都附加上下文。剥离入口（`stripTypeScriptTypes`，amaro 的 `SyntaxError` 无位置）附加共享补救提示与尽力扫描：`unclosedLiteralHint` `在程序内追踪引号/注释状态，点名未闭合字符串或模板字面量的起始行——主流形态即一个未闭合引号吞掉程序其余部分。worker 侧 `prepareException` 对 `SyntaxError` 报消息加提示并丢弃无信息量的合成栈。

## 备选方案

- **带源映射位置重抛。** 剥离器不给可映射偏移；嵌入行表会把本包耦合进 amaro 内部，而线性扫描已提供该提示。
- **把整个程序回显进错误。** 程序已在失败的工具调用里；回显让载荷翻倍只为一行话就能说清的事。

## 影响

扫描是启发式的：跨正则样式结构开合的字符串可能误报起始行，但绝不遮蔽原始消息——提示只追加，V8 文本在前。注释与转义状态已被追踪；无开放字面量的括号失衡仍无位置上报，由提示的补救路径（先写文件、保持内联体最小）覆盖。

## 测试

`packages/code-runtime` 套件钉住两个面：剥离阶段用例断言未闭合字符串与模板的起始行及提示后缀；`bootstrap.spec` 覆盖 worker 侧提示与栈丢弃。
