# Agent Note: Catalog-route model discovery asks the endpoint first

Status: implemented

English | [中文](2026-08-27-catalog-route-discovery-asks-endpoint.md)

## Problem

内置提供方路由上的「获取可用模型」直接以构建时捆绑的 pi-ai catalog 作答，从不联网。catalog 是构建时快照（pi-ai 0.82.1，生成于 2026-07-25），因此提供方在快照之后发布的模型——报告的案例中是智谱的 `glm-5.3` 与 `glm-5.3-flash`——无论用户键入什么密钥都永远不会出现。这个动作承诺的是「从提供方拿当前列表」，而在 catalog 收录的每一条路由上（恰恰是多数用户的起点）这个承诺从构造上就无法兑现。端点本身从来不是问题：智谱路由的 `GET /models` 回答的就是标准 OpenAI 列表形状。

## Decision

`discoverModels` 把 catalog 路由的捆绑条目当作回退，而不是答案。已安装 catalog 收录的路由现在先询问自己的端点——草稿点名的 `baseURL`，否则用 catalog 提供方自带的——并把回复叠加到已安装条目上：端点给出的 id 按端点顺序构成当前答案，公布的容量胜过捆绑值，catalog 也描述过的条目在列表未公布处沿用已安装的名称与容量。所有无法询问的情形都并入注册表回退：协议没有可读列表的路由、任何端点都不存在的路由、无法解析或无法放进 HTTP 标头的凭据，以及端点回答的每一次拒绝或故障。只有取消会浮出，呈现为 `ABORTED`。catalog 未描述的路由保持不变：仅经协议层询问，拒绝照常浮出。

联网询问收敛为一个共享的 `interrogateListing` 辅助函数；草稿路径保留其编码失败，catalog 路径把它们接住并入回退。

## Alternatives considered

**保留注册表答案，等 pi-ai 升级。** 否决：快照从生成那天起就在老化，而用户抱怨的是今天已存在的模型。catalog 刷新周期仍会让每个构建在版本之间处于过期状态。

**去掉 catalog 短路，一律联网询问。** 否决：这会让离线用户走进死胡同，并把每条不可列表的 catalog 路由（anthropic、bedrock、azure、codex）变成 `DISCOVERY_UNSUPPORTED`，倒退掉短路当初要保证的东西——catalog 路由总能作答。

**除认证拒绝外都回退，让错误的密钥仍能浮出。** 否决：首次运行姿态——还没存也没键入密钥——会不带认证探测，这样会用注册表答案换回一条用户此刻无法着手处理的「检查 API 密钥」错误。探测是候选列表，不是凭据测试；草稿路由仍然是凭据故障浮出的地方。

**让「配置点名了 apiKeyEnv 但未存储」的凭据在 catalog 发现场合大声失败。** 否决：发现是候选列表，不是凭据健康检查。点名了 `apiKeyEnv` 而密钥未存档的 profile 在此按设计折叠进注册表答案；请求路径仍会抛 `MISSING_CREDENTIAL`——凭据健康归属那里，用户也只在那里能着手处理。

## Consequences

catalog 路由的获取从零成本变成一次网络往返，响应慢的提供方端点会延迟选择器，而过去注册表是即时作答的；回退兜住的是失败，不是延迟。存了错误密钥的用户看到的是捆绑列表而非认证错误——与变更前的答案相同——因此选择器的列表恰在端点能回答时才是当前的，路由的凭据健康仍然只能由一次真实请求证明。测试钉住了叠加的顺序与容量、每一种回退折叠、无可列表与无端点两种姿态，以及取消仍然浮出。
